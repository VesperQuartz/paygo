# better-result adoption audit — PayGo

Status: **Slice A implemented** (Channel3 read path); slices B/C still pending approval
Audited: 2026-10-18 · better-result v3.0.1 · Slice A landed 2026-10-18

## 1. Scope and repository facts

- **Repository:** `paygo` — PayGo, a "never overpay" shopping assistant. TanStack Start (React 19) on the Vite+ toolchain, better-auth, Drizzle + Neon Postgres, oRPC, Hono, Tailwind v4 + shadcn/base-ui.
- **Validation commands:** `vp check` (format + lint + typecheck), `vp test run` (**no test files exist** — manual/live verification is the current practice: SSR curl + browser checks), `vp dev`.
- **Installed library:** `better-result@3.0.1` (ESM-only, zero runtime deps), installed but **not yet used anywhere** in `src/`. `@praha/byethrow` and `effect` are also in `package.json` but unused here; this audit adopts better-result exclusively.
- **API verified against installed package** (`node_modules/better-result/README.md`, `dist/index.d.mts`):
  - `Result.ok / err / try / tryPromise`, instance + static combinators (`map`, `mapError`, `andThen`, `tryRecover`, `tap*`, `match`, `unwrapOr`, `unwrap`), async composition via `Result.gen` + `Result.await`, collections via `Result.all / allAsync / partition / partitionAsync / flatten`.
  - `TaggedError("Tag")<Props>` classes with `X.is()`, exhaustive `.match()`, `.toJSON()`; `matchError` / `matchErrorPartial` for structural tags.
  - Boundaries: `Result.codec({ serialize: {ok, err}, deserialize: {ok, err} })` with Standard Schema validators; `serializeUnsafe` / `deserializeUnsafe` when producer and consumer are owned and versioned together; `ResultSerializationError` / `ResultDeserializationError`.
  - Defects: `Panic`, `panic(message, cause)`, `isPanic`; `UnhandledException` fallback.
- **Excluded from migration (vendored/generated):** `src/components/ui/*` (shadcn), the Channel3 UI-registry components (`src/components/product-*.tsx`, `search-bar.tsx`, `offers-list.tsx`, `image-gallery.tsx`, `variant-selector.tsx`, `price-*.tsx`) and registry hooks (`src/hooks/use-product-*.ts`, `use-variant-selection.ts`, `use-async-options.ts`, `use-in-viewport.ts`), `src/routeTree.gen.ts`, `src/repo/schema/auth.schema.ts`. Two tiny registry patches already exist (base-ui prop fixes) as precedent for surgical UI patches.

## 5. End-to-end propagation paths (representative)

- **P1 — Search failure (worst current gap):** user submits query → block → `fetchSearch` → `searchProducts` server fn → `client.products.search` → SDK rejection → server-fn 500 → TanStack Query `error` (unknown) → `useProductSearch.error` → **never rendered**; the grid shows the initial empty-state text as if no search was made. No state mutated; safe.
- **P2 — PDP load:** loader `Promise.all([getProduct, getPriceHistory.catch→null])` → `getProduct` failure throws → generic `DefaultCatchBoundary` page ("Try Again"); history failure silently hides the section; failure vs no-data indistinguishable (F2/F4/F5 conflation).
- **P3 — Variant re-resolve:** select variant → `getProductFn` → failure → `setError(caught)` → unrendered; UI silently reverts the selection. Safe state (selection only applied on success).
- **P4 — PayPal create:** button `createOrder` → server fn → `services/paypal` → failure or missing id → mutation rejection → PayPal SDK's own error surface only; no app messaging.
- **P5 — PayPal capture (money-critical):** approve → `capture.mutateAsync` → failure → **unhandled rejection inside `onApprove`**; no toast; user cannot tell whether they were charged. Capture may have partially succeeded upstream → retry/idempotency policy required before any "try again" affordance.
- **P6 — Signup verification mail:** better-auth `sendVerificationEmail` → `MailServer.sendVerificationEmail` → nodemailer → rejection propagates into better-auth's signup response (exact surface unverified — unknown U3).

## 7. Proposed tagged errors and Panic sites

New tagged errors (fields minimized to safe data):

- `Channel3Unavailable { operation, statusCode?, message }` — F2
- `Channel3RequestRejected { operation, statusCode, detail?, message }` — F3
- `ProductNotFound { productId, message }` — F4
- `PayPalOrderCreateFailed { statusCode?, message, cause }` — F6 (cause internal-only)
- `PayPalOrderIdMissing { message }` — F7
- `PayPalOrderCaptureFailed { orderId, statusCode?, message, cause }` — F8
- `EmailDeliveryFailed { recipient, kind, message, cause }` — F10 (slice C)
- `SessionLookupFailed` — F9 candidate, pending contract verification

Panic sites: `getChannel3()` missing key (F1); codec `deserializeUnsafe` (by design). Kept throws: registry guards (F20), framework redirect (F19), env boot validation (F18).

`UnhandledException` fallback: **none planned initially** — each external SDK's documented failures map to the tags above; anything unmapped surfaces as a defect (panic/500) and is logged for a follow-up row. This keeps the fallback list empty and visible.

## 9. Ranked vertical migration slices

1. ✅ **Slice A (implemented): Channel3 read path.** `actions/channel3` (4 operations) + `lib/channel3` + search seam (route fetcher + small registry error-notice patch) + PDP loader (`notFound()` for F4, inline retry card for F2/F3, split F5 from failures) + variant `onError` toast. **Why first:** highest-traffic core UX, fixes today's silent failures (P1–P3), and establishes the ServerFn codec + TaggedError pattern that every later slice reuses. Read-only: no state/compensation risk.
   - Landed: `src/lib/channel3/{errors,classify,wire,messages}.ts` (TaggedError union, SDK-error classifier, `Result.codec` wire, user/dev message maps); `actions/channel3` returns `SerializedResult` (`callChannel3` + failure logging); missing key → `panic()`; `throwOnChannel3Error` adapter seam for vendored consumers; minimal vendored patches (`use-product-search` `retry`, `product-search` error branch via new `search-error-notice.tsx`); `/search` + `/product/$id` codec adapters, `notFound()` → 404 page, route `errorComponent` retry card, variant `onError` toast.
   - Recorded deviations: wire error payloads expose only stable fields (`{_tag, operation, statusCode}`, `{_tag, productId}`, `{_tag}`) — no `message`/`cause`/`stack`; history 404 → empty `Ok` (no history is a normal state); non-SDK causes fall back to `UnhandledException` (temporary, revisit if such failures prove common).
2. ✅ **Slice B (implemented): PayPal orders + subscriptions.** `lib/paypal/{errors,messages,wire}.ts` (tagged failures incl. subscription variants, order codecs), `services/paypal` rewritten Result-first (`createPayPalOrder`; capture with `paypalRequestId: paygo-capture-${orderId}` + `getOrder` verification recovery — `COMPLETED` treated as success, no blind retry; `createPayPalSubscription` / `fetchPayPalSubscription`), `actions/paypal` envelope codecs, demo button toasts + flow abort on create failure. Subscription flow: create at PayPal → buyer approves in the SDK modal → `confirmProSubscription` requires live `ACTIVE` status before storing; `syncProSubscription` lazily re-reads; no webhooks.
3. ✅ **Slice C (implemented): Mail + auth callbacks.** `services/mail` rewritten Result-first (`sendVerificationEmail` / `sendPriceDropAlert` → `Result<MailSent, EmailDeliveryFailed>`); `auth.ts` callback policy: rethrow the tagged error — the explicit resend endpoint surfaces it to the client while better-auth's `runInBackgroundOrAwait` swallows it for signup/sign-in (so mail outages never block account creation). Also fixed the verification template itself: it previously rendered an **empty body** (no link, plus a token-URL console.log), i.e. no user could ever verify; both templates now render real content and are pinned by tests.
4. ✅ **Slice D (not a migration): phase 3 watchlist DB code, written Result-first.** Landed with phase 3: `repo/watchlist.repo.ts` wraps every query in `Result.tryPromise` → `WatchlistStorageError {operation, cause}` (cause logged server-side only) and returns domain entries; `lib/watchlist/{errors,wire,messages}.ts` mirror the channel3 pattern (tagged errors, `Result.codec` wire with ISO timestamps, user message map). No legacy DB code needed migration.

## 10. Unknowns and decisions needed

- **U1:** Depth of ok-payload validation for vendor-owned types (Channel3 `Product`). Decision recorded in §6-A: envelope strict, payload minimal+passthrough; revisit if requirements change.
- **U2:** ✅ resolved in slice B: thrown SDK failures are `@apimatic/core` `ApiError` with `{ message, statusCode, headers, body, request }` (verified live: capture without approval → 422 `ORDER_NOT_APPROVED`). The `statusOf(cause)` classifier lives in the service layer only, so `lib/paypal/errors.ts` stays dependency-free for client bundles.
- **U3:** ✅ resolved in slices C/D (from better-auth 1.7.7 source): signup + send-on-sign-in call the callback through `runInBackgroundOrAwait`, which catches and logs rejections (`"Failed to run background task"`), so signup succeeds even when mail fails; the standalone `/send-verification-email` endpoint awaits the callback directly, so a rejection surfaces as a client error. Phase-3 flow verified the same in practice for `getSession` (null → tagged unauthenticated; a store failure would throw into the storage-error branch).
- **U4:** ✅ resolved in slice A: TanStack Start/seroval pass the returned `SerializedResult` envelope through untouched (verified live: search results, PDP payloads, reconstructed tagged errors on the client).
- **U5:** ✅ done in slice C — `afterEmailVerification` now logs only the opaque user id (was the full user object), and the template's token-URL `console.log` is gone.
- **U6:** Chat route + oRPC starter surfaces — out of scope unless kept for production.
